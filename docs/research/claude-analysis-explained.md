# Claude의 현대차 차량용 앱 공모전 분석을 쉬운 한국어로 풀어보기

작성: 2026-11-05. 바탕 자료: `claude-original-2026-11-05.txt`.

**중요: 이 문서는 사용자가 제공한 Claude 조사를 이해하기 쉽게 재구성한 것이다.** 원문에 있는 VERIFIED는 'Claude가 직접 확인했다는 주장'이지, 이 저장소 작성자가 모든 출처를 재검증했다는 의미가 아니다. 공모전 일정·제출 규칙·심사 항목만 별도로 공식 홈페이지에서 재확인했다.

## 1. 현대차가 만들고 싶은 자동차는 무엇인가

현대자동차가 추진하는 소프트웨어 중심 자동차(SDV)는 출고 시 기능이 결정되는 자동차를 넘어, 소프트웨어 업데이트와 앱을 통해 이용 경험이 계속 변화하는 자동차를 뜻한다. 이런 방향에서 Pleos는 현대차그룹의 소프트웨어·모빌리티 브랜드이고, Pleos Connect는 자동차 안에서 여러 앱과 기능이 실행되는 플랫폼이다.

Claude 조사에 따르면 현대차는 차량에서 수집되는 정보를 활용해 서비스와 소프트웨어를 개선하고, 다시 자동차에 반영하는 흐름을 중시한다. 이를 보고서에서는 '데이터 플라이휠'이라고 부른다. 이해하기 쉽게 말하면, 자동차가 실제 사용 과정에서 얻은 정보를 서비스 개선에 활용하고 그 결과가 다시 사용 경험을 높이는 순환 구조다.

여기서 주의할 점은 '현대차가 특정 신호를 모든 외부 개발자에게 실시간으로 제공한다'는 뜻이 아니라는 것이다. 공개 SDK와 접근 권한 안에서 활용 가능한 데이터만 우리 앱에 쓸 수 있다.

## 2. 왜 음악·지도 앱을 하나 더 만드는 것은 약할 수 있을까

Claude가 조사한 당시 Pleos 앱마켓은 상대적으로 초기 단계이며, 이미 존재하는 앱을 자동차 화면에 맞게 옮긴 사례가 많다는 분석이었다. 스마트폰에서 제공하는 기능을 그대로 옮기면 사용자에게 익숙하다는 장점은 있지만, 자동차 환경만의 특별한 가치를 증명하기는 어렵다.

이번 공모전은 '차량특화성'을 별도 심사 항목으로 평가한다. 따라서 '스마트폰에서 실행해도 동일한 서비스인가?'라는 질문에 답해야 한다. 자동차의 상태, 이동, 승하차, 탑승 인원, 배터리, 공조 같은 정보가 없으면 성립하지 않는 경험을 찾아보자는 것이 핵심이다.

**공식으로 확인된 사실:** 차량특화성, 창의성, 기술 활용성, 사업성은 1차 심사 항목이며 세부 배점은 공개되지 않았다.

## 3. 현대차가 이미 제공하는 서비스는 되도록 피해 가자

Claude가 조사한 사례에는 마이현대의 차량 관리, 운전 패턴 분석, 안전운전 점수와 일부 전기차 충전 경로 기능, 음성 비서 등이 있다. 이 주제를 그대로 다시 만들면 '기존 서비스보다 무엇이 새롭나?'라는 질문을 받기 쉽다.

그렇다고 안전·전기차·차량 관리 주제가 모두 금지된 것은 아니다. 예를 들어 단순한 배터리 잔량 표시 대신 실제 주행 데이터를 시간에 따라 수집하고, 외부 기온과 경로 조건을 비교해 예측 오차를 줄이는 문제는 다른 기획이 될 수 있다. 다만 현재 서비스와 얼마나 다른지는 별도 경쟁조사가 필요하다.

## 4. 개발자가 차량에서 읽을 수 있는 정보는 생각보다 넓지만 한계도 있다

Claude 조사에는 와이퍼 작동 상태, 전조등·안개등, 좌석 점유 및 안전벨트, 배터리 상태와 전비, 주행거리, 공조 상태, 일부 타이어 정보 등이 후보 데이터로 제시된다. 이런 정보는 일반적인 스마트폰 앱으로는 직접 알기 어렵다.

하지만 SDK 문서에 '타이어'가 있다고 해서 모든 차에서 네 바퀴의 정확한 공기압 수치를 읽을 수 있다는 증거는 아니다. '공조 온도'가 있다고 해서 실외 기온과 실내 기온을 모두 확인할 수 있다는 의미도 아니다. 위치 SDK가 문서에 있다고 해서 현재 계정에서 권한 없이 동작한다는 보장도 없다.

또한 Claude는 전방 충돌 경고, 페달 오조작 경고, 외부 기온 등에 대한 API를 당시 확인하지 못했다고 적었다. 이는 '절대 제공하지 않는다'는 증명이 아니라 조사 범위에서 확인되지 않았다는 의미로 읽어야 한다.

따라서 SDK 메서드 이름, 반환 타입, permission, 지원 차종, 에뮬레이터 주입 가능 신호를 각각 검증하고 그 결과만 문서에 기록해야 한다.

## 5. 이전 수상 사례가 주는 힌트

Claude는 현대차·기아 사내 해커톤과 다른 완성차 공모전의 사례를 비교했다. 사내 해커톤의 대상 사례로는 주행과 도착 시점을 아동용 오디오 스토리에 결합한 아이디어가 제시됐다. 이 사례의 흥미로운 지점은 단순히 아이에게 오디오를 들려주는 게 아니라 '자동차가 목적지에 도착하는 순간'이라는 맥락을 경험의 일부로 썼다는 데 있다.

그러나 이런 패턴을 이번 외부 공모전의 당선 공식이라고 볼 수는 없다. 참가자, 심사위원, 경쟁작, 평가 기준이 다를 수 있기 때문이다. 우리는 사례에서 '구체적 사용자 + 차에서만 발생하는 순간 + 검증 가능한 혜택'이라는 문제 정의 방법을 배울 수 있다.

## 6. 기술적으로 무엇을 차별화할까

사용자는 단순히 LLM에 차량 데이터를 보내 'AI 추천'을 받는 앱을 원하지 않는다. 실제 데이터 수집과 분석이 핵심이어야 한다.

가능한 접근은 차량 SDK로 특정 상태 변화를 기록하고, 그 시각과 위치에 대응하는 외부 데이터를 수집해 두 데이터를 비교하는 것이다. 예컨대 와이퍼 상태와 기상청 관측값의 불일치를 살펴보거나, 공조 설정 변화와 사용자 체감 쾌적도를 비교하는 식이다.

실제 데이터에 기반한 규칙, 통계, 오차 측정이 먼저이고 AI는 꼭 필요한 경우에만 보조 수단으로 고려한다.

## 7. 왜 초기 개발 목표를 작게 잡아야 하나

제출 마감은 2026년 11월 15일이다. 1차는 기획서만으로도 접수 가능하지만 프로토타입과 시연 영상, 소스 코드 및 APK는 가산점 요소이고, 2차 진출 시에는 실제 동작 앱이 필요하다.

따라서 지금은 여러 서비스를 동시에 구현하지 않는다. 먼저 '차에서만 가능한 문제'를 찾고, 꼭 필요한 신호 한두 개가 실제로 읽히는지 확인한다. 이후 '차량 상태 변화 → 데이터 기록 → 판단 결과 → 차량에 적합한 화면'의 짧은 흐름으로 핵심 경험을 시연하는 것이 현실적이다.

## 8. 아직 확정하지 않은 것

- 최종 아이디어와 서비스 이름
- Kotlin 앱만으로 구성할지 Spring Boot와 PostgreSQL이 필요한지
- 위치 정보를 활용할지, 위치 동의를 어떻게 받을지
- 실제 여러 자동차가 필요한지, 에뮬레이터 한 대로 검증 가능한지
- 사용자가 얻는 가치를 무엇으로 측정할지

**요약:** 차량이 수집할 수 있는 고유한 신호를 출발점으로 삼되, 기술을 먼저 고르지 말고 해결할 사용자 문제를 고르자. 아이디어는 아직 미확정 상태다.
