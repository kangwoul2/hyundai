# ADR-001: BabyRelay MVP 범위 확정

- 상태: 채택 (2026-11-05, 사용자 지시)
- 선행: `docs/process/decision-log.md`의 "아이디어 미확정(OPEN)" 상태를 이 결정이 대체한다.

## 배경

설계 검토 보고서의 판정은 CONDITIONAL이었다. 공모전 심사 항목(차량특화성, 창의성, 기술 활용성, 사업성)과 1~2주 개발 일정, 서버 운영 부담을 함께 고려해야 했다.

## 결정

| # | 결정 | 이유 |
| --- | --- | --- |
| 1 | 서버(Spring Boot 등)를 두지 않는다 | 다중 사용자 집계가 필요 없고, 개인정보 최소화에 유리 |
| 2 | 실시간 보호자 인계를 제거하고 "목적지 도착 카드"로 축소 | 인증·동기화 비용이 큼. 도착 시점 카드로도 핵심 가치 전달 |
| 3 | 핵심 SDK는 NaviHelper | 경유지 등록과 도착 이벤트가 차량 고유 가치의 핵심 |
| 4 | Pleos Adapter와 Replay Adapter를 분리, 같은 도메인 로직 사용 | SDK 불가 상황에서도 검증·시연 가능, 단 실차 검증을 대신하지 않음 |
| 5 | 추천은 설명 가능한 규칙 기반 | 이유 문장을 계산값과 일치시켜 검증 가능 |
| 6 | 상태 머신(내비 사실)과 UxPolicy(플랫폼 주행 제한)를 분리 | 도착 이벤트 ≠ 정차. 안전 정책을 한 조건으로 섞지 않음 |
| 7 | Kotlin + Compose + MVVM + StateFlow + Room, 수동 DI | 소규모, 프레임워크 추가 최소화 |

## 결과

- 장점: 오프라인 동작, 개인정보 서버 전송 없음, JVM 테스트 가능한 도메인.
- 단점/위험: 시설 데이터가 로컬 스냅샷이라 갱신이 느림(실데이터 미확보 → SAMPLE). 실제 경로 ETA가 없어 직선거리 기반 근접 후보로 표시(우회 시간을 만들어 내지 않음). 실제 Pleos 검증 결과에 따라 차량특화성 주장이 달라진다.

## 재검토 조건

실제 Pleos 에뮬레이터에서 경유지 포함 경로 요청이 지원되지 않는다고 확인되면, 인계/도착 카드 중심으로 가치 제안을 재정렬하고 약점을 위험으로 기록한다(`docs/development/sdk-integration.md`).
